# Build Plan — Sandbox MMO-ARPG pivot

Companion to [`PIVOT_PLAN.md`](PIVOT_PLAN.md), which holds the design. This file is the
**execution order**: what to build, in what sequence, and how each phase proves itself.

**Sizing** is effort for one experienced engineer, because team size and calendar are still open:
**S** = days · **M** = 1–2 weeks · **L** = 3–6 weeks · **XL** = 2–3 months.
Art and audio are **not** included in the sizes; they're called out separately where they gate work.

**Branch:** `pivot/mmo`. `master` keeps the current playable co-op game until the experiment
earns the swap.

---

## Rules that hold for every phase

1. **Stay runnable.** Every phase ends in something you can launch and play. No phase may leave
   the build broken "until the next one lands."
2. **`sim/` and `world/` never import graphics.** Enforced by a headless build target in
   `test.sh`, from P0 onward. This is what makes a dedicated server possible at all.
3. **The server is the authority** on items, gold, skills and positions from P2 onward. The client
   only asks.
4. **The economy ledger (§5.9) logs from its first day.** Every gold or item faucet and sink,
   with a reason code. It can't be reconstructed later.
5. **Content is data, not code.** Items, recipes, nodes, skills, NPC demands, reserve policies all
   live in `data/` and hot-reload.
6. **Every phase adds its tests to `test.sh`.** The repo already has the habit
   (`combat_rules_test`, `game_logic_test`, `p2p/protocol_test`); keep it.

---

## Phase map

| Phase | Goal | Size | Gate it passes |
|---|---|---|---|
| **P0** | Foundation, no behaviour change | **L** | server package builds headless; game plays as before |
| **P1a** | raylib → sokol, 2D parity | **L** | current game runs, raylib deleted |
| **P1b** | Top-down 3D | **XL** | same game, 3D models, free camera |
| **P2** | Dedicated server + persistence | **XL** | 50 real + 500 simulated players |
| **P3** | Vertical slice: the whole loop, thin | **XL** | mine → smith key → dungeon → salvage → sell |
| **P4** | Widen systems and content | **XL** | all skills, raids, enchanting, services |
| **P5** | Scale and harden | **L** | 2,000-player shard |
| **P6** | Playtest and live-ops prep | **L** | external playtest survives a week |

P0–P2 are infrastructure with no new gameplay: this is the expensive, unglamorous stretch.
**P3 is the first moment the pivot can be judged as a game.** Consider pulling its design
questions (keepsake rules, pacing) forward into playtests the moment the loop closes.

## P0 — Foundation (size **L**)

Done on the current raylib build. No visible change; everything here is a prerequisite that
gets harder later.

**Tasks**
- [~] **Package split** (`PIVOT_PLAN.md` §4.3) → `sim/` `world/` `net/` `backend/` `client/` `server/` `editor/`
  - [x] **Slice 1 — the core** is in `src/sim/`: `components.odin`, `ecs.odin` (`World`,
        `Simulation`, ECS wrappers), `players.odin`, `core_systems.odin` (`movement_system`,
        `self_destruct_system`). It imports only clockwork. `src/sim_aliases.odin` (generated by
        `tools/gen_sim_aliases.py`) re-exports these names into `main`, so no other file changed.
        Odin `::` aliases are the same entity, not a copy.
  - [ ] **Correction to the original plan:** "imports no raylib" does *not* mean "movable". Odin
        forbids cyclic imports, so a file can move into `sim` only if nothing it calls stays in
        `main`. `ai_system`, `damage_system`, `weapon_system`, `items` etc. call presentation
        directly: `play_sfx`, `camera_shake`, `push_dmg_number`, `push_explosion`, `ui_mark_dirty`.
        **Next slice:** add a `sim.Presentation` hooks struct (proc pointers, no-op by default;
        the client sets them at startup, the server leaves them empty). Then those systems can move.
  - [ ] Shrink `sim_aliases.odin` over time by qualifying call sites as `sim.Name`; delete it at zero.
- [x] **Headless build target.** `./build.sh server` → `bin/tormentas_server` (`src/server/`).
      `test.sh` now:
      - enforces import rules (`tools/check_boundaries.py`)
      - builds the server
      - **fails if the binary links any graphics/audio/UI/Steam symbol**, catching indirect
        dependencies too
      - runs it with invariant checks
      Debug binary is 775 KB vs the game's 6.8 MB, with 0 forbidden symbols vs the game's 4,925.
- [ ] **Fix the destroy-path entity leak** (found by the new `sim` tests). `world_tag_destroy` sets
      `.ToDestroy` itself, so clockwork's `world_mark_destroy` early-returns in `world_reap_tagged`
      and the id never reaches `pending_destroy`. Every projectile and self-destruct keeps its slot
      until the level is cleared, and `world_is_valid` stays `true` for it. Gameplay is unaffected
      (queries skip it); memory isn't, and a persistent server never clears. A one-line fix
      (call `ecs.world_mark_destroy` inside `world_tag_destroy`), but it changes `world_is_valid`
      for dead ids, so ship it **as its own change with a playtest**, then tighten
      `self_destruct_expires_on_host_only`.
- [ ] **`build.ps1` server target + Windows symbol check.** `test.ps1` already runs the `sim` suite;
      the server build and the `dumpbin` equivalent of the `nm` check are macOS-only so far.
- [ ] **Spatial hash** replacing the all-pairs loop in `separation_system.odin:12`. Needed for
      scale, and a win for the current game too.
- [ ] **`ItemDef` / `ItemInstance` split** (§5.2). Today `SavedItem` inlines every base stat, the
      name, the icon and the description per item. Move definitions to `data/items/*.json`;
      instances keep id, def, qty, durability, quality, enchants.
- [ ] **Save migration** for the item change (`SAVE_VERSION` 7 → 8), or an explicit wipe. The
      roadmap already flags migration policy as undecided; decide it here.
- [ ] **Economy ledger skeleton** (§5.9): `EconomyEvent`, reason codes, an append-only sink. Wire
      the faucets and sinks that already exist (gold drops, shop buy/sell).
- [ ] **Snapshot fairness fix** in `netcode.odin:78`: sort by distance to each client before the
      256-entity cap, instead of query order. Today a monster next to you can be the one dropped.

**Exit:** the game plays exactly as it did; `./test.sh` builds a headless server package.
**Verify:** existing tests pass · a new import-boundary test · a save round-trip test across the
item migration.
**Risks:** the package split touches everything at once. Do it as one mechanical pass driven by
the compiler, in its own commit, with no behaviour changes mixed in.

## P1a — raylib → sokol, 2D parity (size **L**)

**Tasks**
- [ ] Vendor **sokol-odin** and **sokol-shdc** into `deps/` with the provenance + SHA manifest
      convention already used by `deps/clockwork-ecs`. Wire shader compilation into `build.sh`.
- [ ] **Platform layer:** `sokol_app` for window, input and events; **miniaudio** for audio
      (Odin ships it in `vendor:`); **fontstash/stb_truetype** for text.
- [ ] **2D batcher.** About 15 calls cover nearly all of today's 2,449 `rl.` uses: filled and
      outlined rects, lines, triangles, textured quads, text, measure-text, scissor.
- [ ] **Port local types:** `rl.Color` (763 uses), `rl.Rectangle`, `rl.Vector2` → own types.
      Mechanical, large, low-risk.
- [ ] **Clay renderer backend** (`clay_renderer.odin`) onto the batcher.
- [ ] **ImGui backend** for the dev tools (`deps/imgui` is already vendored).
- [ ] Delete raylib and `tools/build-clay.sh` assumptions that depend on it.

**Exit:** the current game, still isometric 2D, runs on sokol with raylib gone.
**Verify:** side-by-side screenshots of hub and a level · input latency unchanged · all dev tools work.
**Risks:** text rendering and the Clay backend are the fiddly parts. Do the batcher first and port
the simplest UI panel end-to-end before touching the rest.

## P1b — Top-down 3D (size **XL**)

**Tasks**
- [ ] **Camera:** top-down orbit, free yaw, clamped pitch, zoom.
- [ ] **Camera-relative input**, and mouse aim by ray-cast to the z=0 plane (easy: the world stays
      a flat grid).
- [ ] **Model pipeline:** glTF via `vendor:cgltf`, skinned meshes, an animation state machine fed
      by the existing `AnimState` (Idle/Walk/Attack/Death). Sprite facing-flip retires.
- [ ] **World rendering:** instanced tile and prop meshes, chunk frustum culling (same chunk grid
      as AoI and the spatial hash — pick the numbers once).
- [ ] **Lighting:** directional light + shadow map + fog, remapping `LevelLightingConfig`, which
      already carries sun direction, colour and fog.
- [ ] **Cutaway/fade** for geometry between camera and player. Free rotation makes this mandatory,
      not polish.
- [ ] **Placeholder art:** capsules and a few free rigged models so gameplay never waits on art.

**Exit:** the current content is playable top-down in 3D with a free camera.
**Verify:** frame time at the largest current level · camera never traps the player behind geometry.
**Risks:** this is where real **art dependency** starts. Decide early who makes rigged models;
placeholders carry you to P3 but not past it.
**Gate:** if 3D performance or the art pipeline looks untenable here, that's the cheapest moment
to reconsider, before any server work.

## P2 — Dedicated server and persistence (size **XL**)

**Tasks**
- [ ] **Headless binaries:** `server/world` and `server/instance`.
- [ ] **Transport swap:** Steam P2P sockets → **ENet** (`vendor:ENet`) client↔server. Keep Steam
      for identity and the store. `p2p/` becomes `net/`.
- [ ] **Backend** (in-process at first, behind an interface): SQLite, accounts, characters,
      inventories, `ItemId` minting, **character leases** (§4.2 anti-dupe invariants).
- [ ] **Server-authoritative inventory, gold and skills.** The client requests; the server decides.
      Local `save/*.bin` becomes a cache for offline dev only.
- [ ] **AoI replication:** 16×16-tile cells, per-client subscription, distance priority.
- [ ] **Quantized delta snapshots** (§4.5): ~14 bytes per entity instead of 40, 20 Hz overworld tick.
- [ ] **Load-test client:** headless fake players that walk, fight and trade. Without these you
      cannot test the scale target at all.
- [ ] Re-tune combat for 20/30 Hz; `TUNING.md` was tuned at 60.

**Exit:** 50 real clients + 500 simulated in one world, stable for an hour.
**Verify:** measured bandwidth per client against the §4.5 budget · dupe-attempt tests (double
lease, stale epoch, disconnect mid-trade) · crash-recovery leaves no item in two places.
**Risks:** biggest unknown in the plan. Bandwidth and the DB write path are where it bites; both
are measurable early with the load-test client, so build that client sooner than feels necessary.

## P3 — Vertical slice (size **XL**)

The first phase that produces a *game*. Keep every system thin, but close the whole loop.

**Tasks**
- [ ] **Overworld v1:** generate one region pack with landmarks, save it, then hand-edit. One city,
      one PvP strip.
- [ ] **Editor v2, overworld mode:** paint tiles, place props/landmarks, spawners, resource nodes,
      zone polygons.
- [ ] **Skills (3):** Mining (Earner), Smithing (Spender), one combat skill (Neutral). XP curve,
      milestone unlocks, quest XP hook.
- [ ] **Training-method report** (§5.3.1) running in `test.sh`.
- [ ] **Resource nodes + mob spawners,** server-driven respawn.
- [ ] **Death:** corpse owner-only → public → reserve; keepsake as data; combat timer; logout rule.
- [ ] **One procgen dungeon** — the maze pipeline (BiomeDef → ChunkDef → LevelPlan → stamp →
      populate), with chunks authored in editor chunk mode. One key recipe.
- [ ] **NPC merchants:** supply/demand pricing, basic supplies for sale, NPC repair.
- [ ] **Exchange:** order book for materials, sell fees, collection box, and **the reserve**
      (weekly job, price band, visible seller name).
- [ ] **Economy dashboard** off the ledger: gold created vs destroyed per day.

**Exit (the demo):** *mine ore → smith a dungeon key → run the dungeon → salvage the drops → sell
the materials on the exchange → repair your gear.*
**Verify:** reserve ceiling > every NPC buy price (unit test) · no NPC buy-back loop (unit test) ·
pacing profiles within ±15% · a week-long bot soak showing net gold per day tracking player count.
**Risks:** scope creep. Three skills, one dungeon, one city. Everything else is P4.

## P4 — Widen (size **XL**)

- [ ] Remaining skills and unlock tables; recipes as found/purchased items
- [ ] Salvaging; enchanting/engineering replacing random affixes
- [ ] **Escrowed service orders** (player repair, enchanting for hire)
- [ ] Gear listings on the exchange (non-fungible path)
- [ ] 10-player raids; key tiers and modifiers
- [ ] Editor chunk mode + data mode
- [ ] Mutations → skills, after its design pass (`PIVOT_PLAN.md` §9.1)
- [ ] Quests with gold and skill XP

---

## P5 — Scale and harden (size **L**)

- [ ] 2,000-player shard with load-test clients; crowd caps in cities
- [ ] Backend split into its own process; Postgres if SQLite binds
- [ ] Instance process lifecycle under churn (spawn storms, orphan cleanup)
- [ ] Reconnect, migration, and DB schema versioning
- [ ] Basic server-side sanity checks (speed, reach, action rate)

---

## P6 — Playtest and live-ops prep (size **L**)

- [ ] Telemetry dashboards: economy, skill pacing, retention, dungeon completion
- [ ] Balance passes driven by the reports, not by vibes
- [ ] Wipe policy and character migration
- [ ] External playtest, a week of soak, triage

## Risk register

| Risk | Phase | Mitigation |
|---|---|---|
| Package split churn | P0 | one mechanical commit, compiler-driven, no behaviour changes |
| Clay/ImGui backend port | P1a | port one panel end-to-end before the rest |
| Art pipeline (rigged models) | P1b | placeholders to P3; decide art capacity during P1a |
| Bandwidth at 2k players | P2 | load-test client early; measure against §4.5 before widening |
| DB write throughput | P2/P5 | interface over SQLite from day one so Postgres is a swap |
| Dupes and item fraud | P2 | lease epochs + escrow + ledger; adversarial tests in `test.sh` |
| Economy inflation/deflation | P3+ | ledger from day one; net-gold-per-day as the headline metric |
| Scope creep in the slice | P3 | 3 skills, 1 dungeon, 1 city — anything else is P4 |
| Solo-dev calendar | all | P0–P2 produce no new gameplay; consider a playable 3D single-player milestone at P1b to keep morale and feedback alive |
